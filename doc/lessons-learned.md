# 问题记录与经验教训

目的：防止未来会话重蹈本次踩过的坑。全部为本次实测踩坑后归纳。

## 已解决的问题与经验

### 1. Unicode 编码错误

**问题**：Windows 控制台默认 GBK/cp936，print 非 ASCII（✓/✗/中文）会 `UnicodeEncodeError` 中断脚本。

**解决方案**：
- 脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`（包在 try/except 里）
- 或统一用 `[OK]`/`[!]` 等 ASCII 标记

### 2. saya_107c 冗余

**问题**：Resto 1.1.0 存在两个功能重复的脚本，造成调用混乱。

**解决方案**：删除裸名版本，修改调用链，确保唯一性。

### 3. PNA 引用错配

**问题**：改写引用时使用简单字符串替换导致双前缀问题。

**错误示例**：
```python
# ❌ 错误做法
dec.replace('B沙夜_01L', 'ORG_B沙夜_01L')
```

这会命中已是 `ORG_B沙夜_01L` 名字的**尾巴**，把已改好的名再改一次 → 双前缀 `ORG_ORG_B沙夜_01L`。新名字包含旧名字作为子串，裸替换必踩。

**正确做法**：
```python
# ✅ 正确：用带 NUL 前缀的精确模式
dec.replace(b'\x00' + 旧名, b'\x00' + 新名)
```

显示指令格式为 `<slot>\x00NAME.PNA\x00`，使用 NUL 前缀可以精确匹配。

**附加原则**：
- 每次运行时先检查"已满足则跳过"，保证脚本重复运行安全（幂等性）
- 改写后必须回读验证

### 4. 日文文件名识别

**问题**：脚本中带日文的资源名是 Shift-JIS 编码，不是 UTF-8。

**影响**：
- 搜索/改写 `B沙夜_01L` 这类资源引用必须用 `name.encode('shift_jis')` 构造字节模式
- 标准 `0x34` DISPLAY 正则 `[A-Za-z0-9_]+` 匹配不到含日文的名字，审计时极易漏掉

**解决方案**：
```python
# 正确处理日文资源名
resource_name = 'B沙夜_01L'
byte_pattern = resource_name.encode('shift_jis')
```

### 5. 资源缺失卡死（第三类缺陷）

**问题**：原版脚本引用了 Steam 已删除的转场/背景/遮罩 PNG，引擎在硬载入时找不到文件，直接无响应（卡死），不弹任何错误码。

**症状**：
- `0x33` 硬载入缺失资源 → 卡死（无响应）
- `0x66` 遮罩缺失 → 容忍（静默跳过，仅画面瑕疵）

**解决方案**：从 Miazora 补入 9 个 Steam 已删的转场/背景/遮罩 PNG（EST_1033 等）。

**定位方法**（可复用）：
1. **台词 → 脚本偏移**：在 `zh-CN/Rio.arc` 的 lng 中定位台词 slot，再到解码后脚本里找到对应的文本槽引用偏移
2. **偏移 → 指令**：`ws2.decode()` 后按偏移解析紧随其后的 `0x33/0x34/0x66` 资源引用
3. **三方资源审计**：枚举脚本全部 `.PNA/.PNG/.OGG/.MOS` 引用，逐一对 Steam 安装目录与 Miazora 目录求交集，筛出"仅 Miazora 存在"的资源

### 6. EVRET 偏移指针失效 → 回主菜单（第四类缺陷，致命）

**问题**：改名（ORG_ 前缀）改变脚本长度后，结尾偏移指针未同步更新。

**结构**：
每个 `_H` 场景结尾固定结构：
```
<field u32> 01 82 6e 00 00 00 <float> 00 00 <field u32> 07 EVRET 00 0b <gallery u16> 01 07 <next> 00
```

两个 field（`07` 前 20/4 字节）都是指向 `0b <gallery> 01` 的绝对偏移。

**影响**：
改名在该指令前插入字节会让 `0b` 后移而 field 失效 → EVRET 走 TITLE 分支回主菜单。

**解决方案**：
**任何改动脚本长度后必须跑 `fix_evret_offsets.py` 重算偏移（幂等）**

**注意**：
- `01 82 6e` 的 0x6e82 是常量不是偏移，不用改
- **不止改名会踩这个坑**：任何往脚本里插入指令的操作（如注入 `CG_ACHIEVEMENT` 调用）同样会撑大脚本、移动 `0b <gallery> 01` 的位置
- 因此**任何修改 `.ws2` 内容的脚本（改名、注入、插指令……）收尾都必须跑 `fix_evret_offsets.py`，且要对全部 `_H` 脚本复查，不能只查本次改动涉及的那几个**

### 7. 9X 段位部署时源资源与目标名错配（第五类缺陷）

**问题**：`yozora_ori_115_H` 排查 ev01 报错时，最初把 Miazora 的 `ORI_11S.pna` 误部署成了
`ORI_91S.pna`（本应是 `ORI_90S`）。之后发现脚本实际引用的是 `ORI_90L/90S`，于是补部署了
正确的 `ORI_90S`，但**没有同步纠正/清理那个写错名字的 `ORI_91S`**。后续 `yozora_ori_118_H`
的 ev02 报错排查中，又给 `ORI_91L`（正确，来自原版 `ORI_12L`）部署了资源，却没意识到
同一 slot 家族里的 `ORI_91S` 早已装错——里面其实是 `ORI_11S` 的数据（20 层），而
`yozora_ori_118_H` 需要的是 `ORI_12S`（16 层）的内容。

**症状**：错误消失（该报的 0x39 都不报了），但表现为**背景黑屏，只有立绘方块正常显示**，
且**无任何错误日志**——因为 PNA 本身合法、layer_id 也未越界，只是图层内容/结构完全对不上
脚本预期的场景，引擎不报错但渲染错乱。

**排查陷阱**：这类问题很容易被误诊为"同名冲突需要改名隔离"。本次排查中一度错误地认为
`ORI_13/14`（`yozora_ori_118_H` 同时引用的另外两组资源）存在同名冲突，把它们也改成了
9X 段位（`ORI_92/93`）——但回头用 SHA256 一比对，`ORI_13/14` 在 Steam 与 Miazora 中**内容
完全相同**，根本不存在冲突，改名纯属画蛇添足，必须回滚。

**教训**：
- **改名/重定向前先用 SHA256 确认真的存在冲突**，不要凭"看起来像同一类问题"就动手改
- 每次往 9X 段位部署资源后，**必须回读并核对 `sha(部署结果) == sha(Miazora 源文件)`**，
  不能只看"该 slot 有内容了"就认为部署正确
- 建立 9X 段位到原版资源的显式映射表（见 `doc/pna-resources.md`），部署脚本应从这张表
  读取映射，而不是在多个一次性脚本里各自硬编码，避免同一段位被不同脚本写入不同来源

**定位方法（可复用）**：
1. 无报错但画面错乱/背景黑 → 优先怀疑**资源内容错配**，不是缺失也不是越界
2. 对每个可疑的 9X 段位资源，回读 Chip3A/Graphic 等归档中的实际字节，与 Miazora 源文件
   逐一比对 SHA256
3. 同时核对脚本里对该资源请求的 layer_id 上限是否 `<= layer_count - 1`（用
   `cleanup_and_rewrite.py` 中 `max_id_per_pna` 的 0x34/0x39 关联逻辑，不要用简单正则误读
   槛值，见下方调试技巧）

### 8. Arc 文件 Null Padding 导致哈希不一致

**问题**：`Chip3.arc` 在表结束位置（offset 1640）有 2 字节的 null padding（`\x00\x00`），位于表和数据段之间。`arcbuild.write_arc()` 不保留这个 padding，导致每次读写都产出不同的 SHA256，安装器哈希校验失败。

**症状**：
- 源文件 SHA256 ≠ 安装后文件 SHA256（相差 2 字节）
- 重复写入产生不同哈希（非幂等）
- 安装器验证失败

**原因分析**：
```
Arc 文件结构：
[Header 8] [Table 1634] [Padding 2] [Data ...]
                      ↑ 
                 table_size=1634
                 
arcbuild.write_arc() 直接写：[Header 8] [Table 1634] [Data ...]
不保留 Padding，导致产生的文件少 2 字节
```

**解决方案**：
1. **规范化源文件**：运行一次 `arcbuild.normalize_arc_padding()` 去除 padding，使文件与 `arcbuild` 的标准格式一致
2. **防护机制**：`arcbuild.verify()` 现已加入检查，如果发现 padding 会抛出错误并提示运行规范化
3. **确保幂等性**：规范化后，任何读写都产生相同哈希

**代码示例**：
```python
import arcbuild
from pathlib import Path

arc = Path('asset/Chip3.arc')

# 规范化（去除 padding）
size = arcbuild.normalize_arc_padding(arc)
print('Normalized to {} bytes'.format(size))

# 验证（现已检查 padding）
cnt, fsize, end = arcbuild.verify(arc)
# 若有 padding 会抛异常：
# ValueError: spurious null padding at table end (position 1640). 
#            Run normalize_arc_padding() to remove it
```

**教训**：
- **Arc 文件应有唯一的标准形式**，所有读写工具必须产生相同结果
- **哈希校验前必须保证数据稳定**，特别是在多工具操作的流程中
- **验证函数应主动检测和拒绝非标准格式**，而不是默默接受

### 9. PNA 图层级内容残留（"裸名 CG 也可能被阉割"）

**问题**：一直以为"裸名、Steam/原版内容一致"的 PNA（如 `COM_04L.pna`）不需要处理，实际上 Steam 阉割可以发生在**单个 PNA 内部的部分图层**，而不是整份文件层面。全画布主图被换掉后，与之共同渲染的局部角色动画帧如果不同步处理，会出现光照/画风不融合。

**关键认知（详见 `doc/pna-resources.md`/`doc/technical-solutions.md` 4.6）**：
- 图层的 `box_w`/`box_h` = 该图层内嵌 PNG 自身像素宽高，与画布尺寸无关
- `u0` 哨兵只标记动画分组边界，**不记录"哪组局部帧配哪个全画布状态"**，这个配对关系格式里没有字段可查，只能靠实机验证

### 10. 语音（OGG）资源审计：范围要覆盖到最后一类资源，且比对源要选对

**问题**：此前的资源审计只覆盖了 PNA（图层）和部分 PNG（转场/背景/遮罩），没有把 OGG（语音）纳入范围。实测发现新增还原的 3 个 H 场景全程没有角色语音——偶尔能听到的几句，是因为脚本引用的语音文件名恰好命中了 Steam 现有 `Voice.arc`/`Voice1.arc` 里的**同名但内容不对应**的文件，容易被误判为"部分正常"。

**解决方案**：
- 以**未修改的游戏本体安装目录**为权威比对源，而不是 Miazora 二次打包的补丁分发版。第一版审计曾以 Miazora 为源，误判出几个不存在的"缺口"（Miazora 自身编号断层、用户已确认属于本体其它归档的通用音效），换成本体一比对，问题消失。
- 对脚本引用的归档成员名统一做 stem 归一化（去 `.ogg` 扩展名、去 `_mono` 后缀、转大写、大小写不敏感）后逐一比对，只有双方都有实际字节时才做 SHA256 内容比对判定"一致"或"冲突"——仅凭"归档 A 有、归档 B 没有（按精确字符串匹配）"不能得出"冲突"结论，可能只是命名规则差异导致的假阴性匹配。
- 缺失的文件直接从游戏本体按原文件名精确拷贝部署（无需改名，纯拷贝）。

**教训**：
1. **资源审计清单必须显式列出全部资源类型**（PNA/PNG/OGG/MOS…），逐类过一遍，不能默认"这类应该没问题"就跳过——本次教训正是语音这一整类被漏审计了一轮。
2. **比对源的权威性优先于比对源的便利性**：二次打包的补丁分发版可能自身就有资源缺失或重排，游戏本体安装目录才是更可靠的基准。
3. **审计结果与直觉不符时先问用户，不要自行深挖下结论**（如"缺口"却在别处能找到、"没有源"但用户说保证存在）——这类判断往往需要用户已有的、审计脚本触及不到的背景知识（如哪些资源属于本体的其它归档）。

### 11. 拿"已修复的一侧"当基线 = 自比，闸等于没闸

**问题**：识别图片和谐时先用了「合成画布比对」，且比对对象取了 `asset/`（补丁现状）。`COM_04L.pna` 的图层早被 `layer-repairs.json` 覆盖成原版字节，于是"原版 ⇄ asset"两边同源，差异恒为 0，被判成误报「画面完全一致」。同一个错误口径还盖住了 `KOR_04L.pna`：合成只保留图层表最后一帧，被改绘的那几帧根本没进比较。

**教训**：
1. 比对必须在**两个互不派生的源**之间做（原始安装 ⇄ `backup/`）。凡是下游脚本会写入的那一侧（`asset/`）都不能当基线，只能在判完之后用来看补丁现状。
2. 判"无差异"要先问口径**看到了什么**：动画帧各占一个整幅不透明图层时，展平后只剩最后一帧——这种"一致"是口径的产物，不是画面的性质。
3. 结论要能被第二条独立口径复现：换成图层帧池后，`COM_04` 依旧是无内容删改（重打包 + 重编码 + 水面重绘），`KOR_04` 则立刻暴露出定点擦除。两条口径只在"怎么取可比像素"上不同，比较源相同，才谈得上互相印证。

### 12. 定点擦除在全图尺寸下被看成"空背景"

**问题**：`KOR_04L.pna` 的自动复核结论是**真冲突**（差异层 lid=1，通道差 >8 占 0.0131%、峰值 37、外接框 57×57），但人工复核时按这个外接框在全图里看，判成"左上角一小块空背景、无可辨内容改动"，把结论改成误报并零改动。实际那是乳晕被逐点擦除：浅粉覆盖浅肤，擦除区只有 20×24 像素，**在全图尺寸下确实看不出来**，把差区裁出来放大后一目了然。

**解决 / 教训**：
1. **裁定必须看裁差区放大的对照图**，不能拿着外接框坐标回全图上目测。`script/probe/pair_sheet.py … --bbox` 就是把差异外接框裁出来放大到可读宽度，上下拼接原版/Steam 两层。
2. **报告要列出每一个差异层**。逐层复核原先只报"最大差层"，人工就只核那一层；改成逐层列出占比/峰值/外接框，被和谐的那几层藏不住。
3. **幅度阈值判据不唯一**：「占比 < 0.5% 且峰值 ≤ 32 → 噪声级」这条规则与定点擦除可以共享同一组幅度指标（本例峰值 37 侥幸越线），两种成因只有**差异的分布形态**不同 —— 重编码噪声铺满整层，定点擦除只占一小块。因此噪声判据加了例外：差异外接框占可见面积低于 `PINPOINT_BBOX`（5%）时不当噪声，降级为**待定**交人工。
4. 阈值判据要检查它是否**唯一地**刻画了想排除的现象；做不到就补形态指标（外接框、连通域）或退回人工，不要靠调阈值猜。

### 13. 块级「取原版」会整类删掉 Steam 专属 opcode

**表现**：接缝重建（`*_E` → 去 `_E`）后，Steam 独有的指令整类消失且**没有任何报错**，症状只出现在依赖它的功能上（画廊格子不解锁、路线成就弹不出）。

**机制**：`script/seam/build_seam.py` 的 `merge()` 按 block 决策 —— `replace`/`delete` 块整块取原版，块内 `keep_steam` 类的指令只有在**原版同一 block 里也存在同 opcode** 时才被保留（`NOPAIR` 规则）。因此凡是「Steam 有、原版 0 条」的 opcode，落进这类块就必被删除，**与它自己的 `keep_steam` 策略无关**。同理，`replace` 块内的 `0b` 解锁对也会随块消失（即使 `0x0b` 标了 `keep_steam`）。

**推论（做接缝时的检查项）**：

1. `resource/present-ops.json` 里 `counts.orig == 0` 的 opcode **不得**标 `use_orig` —— "取原版"而原版没有 = 必然整类丢失；闸已固化为 `script/checks/check_cg_unlock.py` 的策略自洽项。
2. 块级丢失**不能靠单条 opcode 策略兜住**，必须在脚本级补搬：`script/seam/preserve_cg_unlocks.py`（画廊 `0b` 对 + `CG_ACHIEVEMENT`）、`script/seam/preserve_achievements.py`（`0xf0` 成就调用）。
3. 统计「丢了多少」必须按**指令级**算（独立 `0b` 也算），只按「显示位点后的 id 对」会把「显示被换掉但旗标以独立指令留下」的脚本误报成丢失。

判据与 id 语义见 [file-formats.md](file-formats.md)「CG 显示的固有 id 对」与「`0xf0`：Steam 成就解锁调用」。

## 资源与文件格式缺陷总结

| 类型 | 表现 | 错误码 | 修复方法 |
|------|------|--------|----------|
| 1. 同名冲突 | 渲染失败或画错图 | 0x00000039 | 命名空间隔离（ORG_ 前缀或 9X 段位） |
| 2. 图层 id 越界 | 崩溃 | 0x00000039 | 确保请求 id < layer_count |
| 3. 资源缺失（0x33） | 卡死无响应 | 无错误码 | 从 Miazora 补入缺失的 PNG 资源 |
| 4. EVRET 偏移失效 | 回主菜单 | 无错误码 | 重算并修正偏移指针 |
| 5. 9X 段位源/目标错配 | 背景黑屏，仅立绘正常 | 无错误码 | SHA256 核对部署源与目标一致 |
| 6. Arc 文件非规范格式 | 哈希校验失败 | 无错误码 | 运行 `normalize_arc_padding()` 规范化 |
| 7. PNA 图层级内容残留 | 面部与背景光照不融合 | 无错误码 | 按 box 分组逐层比对，用 Miazora 对应图层替换（`script/tools/replace_pna_layers.py`） |
| 8. 图片级和谐（Steam 改绘保留下来的画面） | 运行正常，但性描写内容缺失 | 无错误码 | 图层帧池比对定位（`script/probe/framepool.py`），再按 1/7 两种方式还原 |
| 9. CG 解锁位点被还原覆盖丢失 | 画廊条目永久锁、全 CG 成就不可达 | 无错误码 | 保留被替换 Steam 脚本的 `[0b A 01 0b B 01][04 CG_ACHIEVEMENT]`，闸：`script/checks/check_cg_unlock.py` |
| 10. Steam 专属 opcode 被块级「取原版」整类删除 | 画廊/成就不可解锁，无报错 | 无错误码 | 脚本级补搬 `0b` 对与 `0xf0`（`preserve_cg_unlocks.py` / `preserve_achievements.py`），闸 `check_cg_unlock.py` |

## 最佳实践

### 脚本改写原则

1. **精确匹配**：使用显示指令上下文（带 NUL 前缀）进行替换
2. **幂等性**：脚本必须可重复运行，每次检查"已满足则跳过"
3. **回读校验**：改写后必须回读验证，确认修改成功
4. **编码正确**：日文资源名使用 Shift-JIS 编码

### 验证清单

改写脚本后必须执行：

- [ ] 调用链完整性检查
- [ ] 资源配对验证（_H ↔ ORG_*/9X，_E ↔ Steam 资源）
- [ ] EVRET 偏移指针修正（如果改变了脚本长度）
- [ ] 资源存在性验证（所有引用的资源都存在）
- [ ] 冗余检测（无重复脚本、无未使用的 ORG_* 资源）
- [ ] 9X 段位内容核对（部署到 9X 段位名下的资源，逐一 SHA256 比对 Miazora 源文件，确认「装的是它自己该装的那份」而不是同批次里另一个资源的数据）
- [ ] Arc 文件规范化检查（运行 `arcbuild.verify()` 检测 null padding；若发现则运行 `normalize_arc_padding()`）
- [ ] SHA256 校验稳定性（修改后重新读写一遍，验证 SHA256 保持一致）

### 调试技巧

1. **遇到 0x00000039 错误**：
   - 检查是否存在同名 PNA 冲突
   - 检查请求的 layer_id 是否超出 layer_count（用 `max_id_per_pna`
     的 0x34/0x39 关联逻辑算真实上限，不要用简单正则去猜 slot 里的 id 字节位置）

2. **遇到卡死无响应**：
   - 定位最后一句台词的位置
   - 检查紧随其后的 `0x33` 资源引用
   - 验证该资源是否存在

3. **场景结束后回主菜单**：
   - 检查 EVRET 偏移指针是否正确
   - 运行 `fix_evret_offsets.py` 修复

4. **资源注册失败**：
   - 优先怀疑资源名问题（特别是 ORG_ 前缀在 ev01/ev02 槽）
   - 用「换成普通新名」的 A/B 测试快速定性
   - 不要过度依赖静态逆向，实机测试更高效

5. **无报错但画面错乱（背景黑屏/局部方块正常）**：
   - 不要一上来就怀疑"同名冲突"去改名隔离——先用 SHA256 比对 Steam 与 Miazora 的同名资源，确认是否真的存在差异，没有差异就不要碰
   - 重点检查最近部署到 9X 段位（或任何改名目标）的资源，是否用 SHA256 核实过 `sha(部署结果) == sha(应该部署的 Miazora 源文件)` —— 同一批次里多个资源容易在改写映射表时张冠李戴
   - 这是"资源存在但内容错配"，PNAP 结构合法、layer_id 不越界，所以引擎不报错，
     纯粹是内容对不上脚本预期

6. **安装器哈希校验失败**：
   - 源 Arc 文件可能存在 null padding（位于表末和数据段之间）
   - 运行 `arcbuild.verify(path)` 检测是否有 padding；若拒绝异常则必须规范化
   - 规范化命令：`arcbuild.normalize_arc_padding(path)`
   - 规范化后重新运行 `generate_payload.py` 生成 `payload/METADATA.json`（安装器校验依据的 checksum 就来自这里），安装器校验应该通过
   - **症状区分**：如果重复读写同一文件产生不同 SHA256，肯定是 padding 问题
