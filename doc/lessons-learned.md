# 问题记录与经验教训

目的：防止未来会话重蹈本次踩过的坑。全部为本次实测踩坑后归纳。

## 已解决的问题与经验

### 1. Unicode 编码错误

**问题**：Windows 控制台默认 GBK/cp936，print 非 ASCII（✓/✗/中文）会 `UnicodeEncodeError` 中断脚本。

**解决方案**：
- 脚本开头加 `sys.stdout.reconfigure(encoding='utf-8')`（包在 try/except 里）
- 或统一用 `[OK]`/`[!]` 等 ASCII 标记

### 2. saya_107c 冗余

**问题**：Resto 1.1.0 存在两个功能重复的脚本，造成调用混乱。

**解决方案**：删除裸名版本，修改调用链，确保唯一性。

### 3. PNA 引用错配

**问题**：改写引用时使用简单字符串替换导致双前缀问题。

**错误示例**：
```python
# ❌ 错误做法
dec.replace('B沙夜_01L', 'ORG_B沙夜_01L')
```

这会命中已是 `ORG_B沙夜_01L` 名字的**尾巴**，把已改好的名再改一次 → 双前缀 `ORG_ORG_B沙夜_01L`。新名字包含旧名字作为子串，裸替换必踩。

**正确做法**：
```python
# ✅ 正确：用带 NUL 前缀的精确模式
dec.replace(b'\x00' + 旧名, b'\x00' + 新名)
```

显示指令格式为 `<slot>\x00NAME.PNA\x00`，使用 NUL 前缀可以精确匹配。

**附加原则**：
- 每次运行时先检查"已满足则跳过"，保证脚本重复运行安全（幂等性）
- 改写后必须回读验证

### 4. 日文文件名识别

**问题**：脚本中带日文的资源名是 Shift-JIS 编码，不是 UTF-8。

**影响**：
- 搜索/改写 `B沙夜_01L` 这类资源引用必须用 `name.encode('shift_jis')` 构造字节模式
- 标准 `0x34` DISPLAY 正则 `[A-Za-z0-9_]+` 匹配不到含日文的名字，审计时极易漏掉

**解决方案**：
```python
# 正确处理日文资源名
resource_name = 'B沙夜_01L'
byte_pattern = resource_name.encode('shift_jis')
```

### 5. 资源缺失卡死（第三类缺陷）

**问题**：原版脚本引用了 Steam 已删除的转场/背景/遮罩 PNG，引擎在硬载入时找不到文件，直接无响应（卡死），不弹任何错误码。

**症状**：
- `0x33` 硬载入缺失资源 → 卡死（无响应）
- `0x66` 遮罩缺失 → 容忍（静默跳过，仅画面瑕疵）

**解决方案**：从 Miazora 补入 9 个 Steam 已删的转场/背景/遮罩 PNG（EST_1033 等）。

**定位方法**（可复用）：
1. **台词 → 脚本偏移**：在 `zh-CN/Rio.arc` 的 lng 中定位台词 slot，再到解码后脚本里找到对应的文本槽引用偏移
2. **偏移 → 指令**：`ws2.decode()` 后按偏移解析紧随其后的 `0x33/0x34/0x66` 资源引用
3. **三方资源审计**：枚举脚本全部 `.PNA/.PNG/.OGG/.MOS` 引用，逐一对 Steam 安装目录与 Miazora 目录求交集，筛出"仅 Miazora 存在"的资源

### 6. EVRET 偏移指针失效 → 回主菜单（第四类缺陷，致命）

**问题**：改名（ORG_ 前缀）改变脚本长度后，结尾偏移指针未同步更新。

**结构**：
每个 `_H` 场景结尾固定结构：
```
<field u32> 01 82 6e 00 00 00 <float> 00 00 <field u32> 07 EVRET 00 0b <gallery u16> 01 07 <next> 00
```

两个 field（`07` 前 20/4 字节）都是指向 `0b <gallery> 01` 的绝对偏移。

**影响**：
改名在该指令前插入字节会让 `0b` 后移而 field 失效 → EVRET 走 TITLE 分支回主菜单。

**解决方案**：
**任何改动脚本长度后必须跑 `fix_evret_offsets.py` 重算偏移（幂等）**

**注意**：
- `01 82 6e` 的 0x6e82 是常量不是偏移，不用改
- 脚本必须幂等，支持重复运行
- **不止改名会踩这个坑**：`inject_achievements.py` 给全部 14 个 `_H` 场景插入
  `CG_ACHIEVEMENT` 调用后同样会撑大脚本、移动 `0b <gallery> 01` 指令位置，一度忘了接着跑
  `fix_evret_offsets.py`，导致此前已修复过的 ori_115_H/ori_118_H 等全部 14 个场景重新
  失效。已跑 `fix_evret_offsets.py` 修复并全量复查通过，同时在该脚本的收尾提示里补上了
  强制提醒。**任何修改 `.ws2` 内容的脚本（改名、注入调用、插入指令……）收尾都必须包含
  这一步，且要对全部 `_H` 脚本复查，不能只查本次改动涉及的那几个**

### 7. 9X 段位部署时源资源与目标名错配（第五类缺陷）

**问题**：`yozora_ori_115_H` 排查 ev01 报错时，最初把 Miazora 的 `ORI_11S.pna` 误部署成了
`ORI_91S.pna`（本应是 `ORI_90S`）。之后发现脚本实际引用的是 `ORI_90L/90S`，于是补部署了
正确的 `ORI_90S`，但**没有同步纠正/清理那个写错名字的 `ORI_91S`**。后续 `yozora_ori_118_H`
的 ev02 报错排查中，又给 `ORI_91L`（正确，来自原版 `ORI_12L`）部署了资源，却没意识到
同一 slot 家族里的 `ORI_91S` 早已装错——里面其实是 `ORI_11S` 的数据（20 层），而
`yozora_ori_118_H` 需要的是 `ORI_12S`（16 层）的内容。

**症状**：错误消失（该报的 0x39 都不报了），但表现为**背景黑屏，只有立绘方块正常显示**，
且**无任何错误日志**——因为 PNA 本身合法、layer_id 也未越界，只是图层内容/结构完全对不上
脚本预期的场景，引擎不报错但渲染错乱。

**排查陷阱**：这类问题很容易被误诊为"同名冲突需要改名隔离"。本次排查中一度错误地认为
`ORI_13/14`（`yozora_ori_118_H` 同时引用的另外两组资源）存在同名冲突，把它们也改成了
9X 段位（`ORI_92/93`）——但回头用 SHA256 一比对，`ORI_13/14` 在 Steam 与 Miazora 中**内容
完全相同**，根本不存在冲突，改名纯属画蛇添足，必须回滚。

**教训**：
- **改名/重定向前先用 SHA256 确认真的存在冲突**，不要凭"看起来像同一类问题"就动手改
- 每次往 9X 段位部署资源后，**必须回读并核对 `sha(部署结果) == sha(Miazora 源文件)`**，
  不能只看"该 slot 有内容了"就认为部署正确
- 建立 9X 段位到原版资源的显式映射表（见 `doc/pna-resources.md`），部署脚本应从这张表
  读取映射，而不是在多个一次性脚本里各自硬编码，避免同一段位被不同脚本写入不同来源

**定位方法（可复用）**：
1. 无报错但画面错乱/背景黑 → 优先怀疑**资源内容错配**，不是缺失也不是越界
2. 对每个可疑的 9X 段位资源，回读 Chip3A/Graphic 等归档中的实际字节，与 Miazora 源文件
   逐一比对 SHA256
3. 同时核对脚本里对该资源请求的 layer_id 上限是否 `<= layer_count - 1`（用
   `cleanup_and_rewrite.py` 中 `max_id_per_pna` 的 0x34/0x39 关联逻辑，不要用简单正则误读
   槛值，见下方调试技巧）

### 8. Arc 文件 Null Padding 导致哈希不一致

**问题**：`Chip3.arc` 在表结束位置（offset 1640）有 2 字节的 null padding（`\x00\x00`），位于表和数据段之间。`arcbuild.write_arc()` 不保留这个 padding，导致每次读写都产出不同的 SHA256，安装器哈希校验失败。

**症状**：
- 源文件 SHA256 ≠ 安装后文件 SHA256（相差 2 字节）
- 重复写入产生不同哈希（非幂等）
- 安装器验证失败

**原因分析**：
```
Arc 文件结构：
[Header 8] [Table 1634] [Padding 2] [Data ...]
                      ↑ 
                 table_size=1634
                 
arcbuild.write_arc() 直接写：[Header 8] [Table 1634] [Data ...]
不保留 Padding，导致产生的文件少 2 字节
```

**解决方案**：
1. **规范化源文件**：运行一次 `arcbuild.normalize_arc_padding()` 去除 padding，使文件与 `arcbuild` 的标准格式一致
2. **防护机制**：`arcbuild.verify()` 现已加入检查，如果发现 padding 会抛出错误并提示运行规范化
3. **确保幂等性**：规范化后，任何读写都产生相同哈希

**代码示例**：
```python
import arcbuild
from pathlib import Path

arc = Path('releases/v1.1.0_fixed/Chip3.arc')

# 规范化（去除 padding）
size = arcbuild.normalize_arc_padding(arc)
print('Normalized to {} bytes'.format(size))

# 验证（现已检查 padding）
cnt, fsize, end = arcbuild.verify(arc)
# 若有 padding 会抛异常：
# ValueError: spurious null padding at table end (position 1640). 
#            Run normalize_arc_padding() to remove it
```

**教训**：
- **Arc 文件应有唯一的标准形式**，所有读写工具必须产生相同结果
- **哈希校验前必须保证数据稳定**，特别是在多工具操作的流程中
- **验证函数应主动检测和拒绝非标准格式**，而不是默默接受

## 资源与文件格式缺陷总结

| 类型 | 表现 | 错误码 | 修复方法 |
|------|------|--------|----------|
| 1. 同名冲突 | 渲染失败或画错图 | 0x00000039 | 命名空间隔离（ORG_ 前缀或 9X 段位） |
| 2. 图层 id 越界 | 崩溃 | 0x00000039 | 确保请求 id < layer_count |
| 3. 资源缺失（0x33） | 卡死无响应 | 无错误码 | 从 Miazora 补入缺失的 PNG 资源 |
| 4. EVRET 偏移失效 | 回主菜单 | 无错误码 | 重算并修正偏移指针 |
| 5. 9X 段位源/目标错配 | 背景黑屏，仅立绘正常 | 无错误码 | SHA256 核对部署源与目标一致 |
| 6. Arc 文件非规范格式 | 哈希校验失败 | 无错误码 | 运行 `normalize_arc_padding()` 规范化 |

## 最佳实践

### 脚本改写原则

1. **精确匹配**：使用显示指令上下文（带 NUL 前缀）进行替换
2. **幂等性**：脚本必须可重复运行，每次检查"已满足则跳过"
3. **回读校验**：改写后必须回读验证，确认修改成功
4. **编码正确**：日文资源名使用 Shift-JIS 编码

### 验证清单

改写脚本后必须执行：

- [ ] 调用链完整性检查
- [ ] 资源配对验证（_H ↔ ORG_*/9X，_E ↔ Steam 资源）
- [ ] EVRET 偏移指针修正（如果改变了脚本长度）
- [ ] 资源存在性验证（所有引用的资源都存在）
- [ ] 冗余检测（无重复脚本、无未使用的 ORG_* 资源）
- [ ] 9X 段位内容核对（部署到 9X 段位名下的资源，逐一 SHA256 比对 Miazora 源文件，
      确认「装的是它自己该装的那份」而不是同批次里另一个资源的数据）
- [ ] Arc 文件规范化检查（运行 `arcbuild.verify()` 检测 null padding；若发现则运行 `normalize_arc_padding()`）
- [ ] SHA256 校验稳定性（修改后重新读写一遍，验证 SHA256 保持一致）

### 调试技巧

1. **遇到 0x00000039 错误**：
   - 检查是否存在同名 PNA 冲突
   - 检查请求的 layer_id 是否超出 layer_count（用 `max_id_per_pna`
     的 0x34/0x39 关联逻辑算真实上限，不要用简单正则去猜 slot 里的 id 字节位置）

2. **遇到卡死无响应**：
   - 定位最后一句台词的位置
   - 检查紧随其后的 `0x33` 资源引用
   - 验证该资源是否存在

3. **场景结束后回主菜单**：
   - 检查 EVRET 偏移指针是否正确
   - 运行 `fix_evret_offsets.py` 修复

4. **资源注册失败**：
   - 优先怀疑资源名问题（特别是 ORG_ 前缀在 ev01/ev02 槽）
   - 用「换成普通新名」的 A/B 测试快速定性
   - 不要过度依赖静态逆向，实机测试更高效

5. **无报错但画面错乱（背景黑屏/局部方块正常）**：
   - 不要一上来就怀疑"同名冲突"去改名隔离——先用 SHA256 比对 Steam 与 Miazora 的
     同名资源，确认是否真的存在差异，没有差异就不要碰
   - 重点检查最近部署到 9X 段位（或任何改名目标）的资源，是否用 SHA256 核实过
     `sha(部署结果) == sha(应该部署的 Miazora 源文件)` —— 同一批次里多个资源
     容易在改写映射表时张冠李戴
   - 这是"资源存在但内容错配"，PNAP 结构合法、layer_id 不越界，所以引擎不报错，
     纯粹是内容对不上脚本预期

6. **安装器哈希校验失败**：
   - 源 Arc 文件可能存在 null padding（位于表末和数据段之间）
   - 运行 `arcbuild.verify(path)` 检测是否有 padding；若拒绝异常则必须规范化
   - 规范化命令：`arcbuild.normalize_arc_padding(path)`
   - 规范化后重新生成 SHA256SUMS，安装器校验应该通过
   - **症状区分**：如果重复读写同一文件产生不同 SHA256，肯定是 padding 问题
