# PNA 资源机制

## 命名规则

PNA 文件分为两大类：**事件 CG** 和**角色立绘**。

### 事件 CG 命名规则

**格式**：`路线代码_场景编号[L/S].pna`

| 路线代码 | 路线名称 | 示例 |
|---------|---------|------|
| COM | 共通线 | `COM_04L.pna`, `COM_01S.pna` |
| HIK | ひかり线 | `HIK_17L.pna`, `HIK_18L.pna` |
| SAY | さや线 | `SAY_20L.pna`, `SAY_23L.pna` |
| ORI | 織姫线 | `ORI_11L.pna`, `ORI_12L.pna` |
| KOR | ころな线 | `KOR_07L.pna`, `KOR_19L.pna` |

**注**：以上均为 Steam/原版共用的裸名资源（无冲突）。补丁新增的 9X 段位事件 CG 见下方
"补丁相关命名"一节（如 `COM_90L.pna`、`ORI_90L/S.pna`）。

**尺寸后缀**：
- `L`：大尺寸（Large）
- `S`：小尺寸（Small）

### 角色立绘命名规则

**格式**：`[字母前缀]+角色日文名_差分编号[L/M/S/W/X].pna`

**主要角色对应关系**：

| 字母前缀 | 角色日文简称 | 角色英文简称 | 示例 |
|---------|-------------|-------------|------|
| A | ひかり | HIKA | `Aひかり_01M.pna`, `Aひかり_02L.pna` |
| B | さや | SAYA | `Bさや_01L.pna`, `Bさや_03L.pna` |
| C | 織姫 | ORI | `C織姫_01L.pna`, `C織姫_02M.pna` |
| D | ころな | KORO | `Dころな_01L.pna`, `Dころな_02L.pna` |

**尺寸/类型后缀**：
- `L`：大尺寸（Large）
- `M`：中等尺寸（Medium）
- `S`：小尺寸（Small）
- `W`：宽屏（Wide）
- `X`：特殊尺寸

### 补丁相关命名

补丁添加的原版 CG 分为两类：**Steam 版差分的 CG（同名冲突）** 和 **Steam 版删除的 CG**。

#### 1. Steam 版差分的 CG - 同名冲突（使用 9X 段位）

**条件**：Steam 版和原版**文件名相同但内容不同**（哈希值不同）

**重要**：一对 CG（L/S）只要有一个文件冲突，整对都使用 9X 段位

**命名规则**：`[ROUTE]_9X[L/S].pna`（7 字节，符合 ev01/ev02 槽限制）

| 原版文件名 | 补丁命名 | 说明 |
|-----------|---------|------|
| HIK_09L/S.pna | HIK_90L/S.pna | HIK_09S 与 Steam 冲突 |
| SAY_15L/S.pna | SAY_90L/S.pna | SAY_15S 与 Steam 冲突 |
| COM_04L.pna | COM_90L.pna | COM_04L 与 Steam 冲突 |
| ORI_11L/S.pna | ORI_91L/S.pna | ORI_11S 与 Steam 冲突 |
| ORI_12L/S.pna | ORI_92L/S.pna | ORI_12L/S 都与 Steam 冲突 |

**重要**：9X 段位仅用于真正的同名冲突，不用于被删除的 CG。

#### 2. Steam 版删除的 CG（直接使用原版编号）

**条件**：Steam 版中**不存在**该编号的 CG

**命名规则**：**直接继承原版编号**（不使用特殊命名）

**补丁添加的 CG**：

| 路线 | 补丁 CG 编号 | 说明 |
|-----|------------|------|
| HIK | HIK_15L/S - HIK_23L/S | 原版编号，Steam 版不存在 |
| SAY | SAY_16L/S - SAY_23L/S | 原版编号，Steam 版不存在 |
| ORI | ORI_13L/S - ORI_19L/S | 原版编号，Steam 版不存在 |
| KOR | KOR_11L/S - KOR_19L/S | 原版编号，Steam 版不存在 |

**原则**：被删除的 CG 不使用特殊命名（如 9X），而是**直接继承原版编号**。

#### 3. 原版立绘（统一使用 ORG_ 前缀）

| 命名模式 | 说明 | 示例 |
|----------|------|------|
| `ORG_[A-D]角色名_##[L/M/S/W/X].pna` | 原版立绘资源 | `ORG_Bさや_01L.pna`, `ORG_Aひかり_02M.pna` |

立绘因为进入 st* 槽（无 7 字节限制），可以使用完整的 `ORG_` 前缀和日文角色名。

### 命名规范说明

**事件 CG 命名约束**：
- ev01/ev02 槽有 **7 字节 stem 硬限制**（见命名空间隔离规则）
- 原版事件 CG 必须使用简短命名：`[ROUTE]_9X[L/S]`（恰好 7 字节，见上方"补丁相关命名"）
- 不能使用长前缀如 `ORG_XXX_##L`（11 字节，超限）

**立绘命名约束**：
- st* 槽无严格长度限制（至少支持 15+ 字节 Shift-JIS）
- 可以使用完整 `ORG_` 前缀：`ORG_Aひかり_01M`

**历史遗留命名（均已废弃，仅供排查旧脚本/旧文档时参考）**：
- `HIK_99L`：曾用作原版 COM_04L 的别名，现已统一为 `COM_90L`
- `ORG_COM_04L`/`ORG_ORI_11L/S`/`ORG_ORI_12L/S`：早期误用 ORG_ 前缀给事件 CG 命名的方案，
  在 ev01/ev02 槽注册必然失败，现已统一为 9X 段位（`COM_90L`、`ORI_90L/S`、`ORI_91L/S`）
- 当前唯一有效的事件 CG 补丁命名规则见上方"补丁相关命名"一节的 `[ROUTE]_9X[L/S]` 格式

## 核心机制：图层 ID 是纯位置量

### 图层编号规则

- **layer_id = layer_count - 1 - index**
- 引擎从文件中按顺序读取图层，倒序编号：
  - 第 0 个图层 → id = layer_count - 1
  - 第 1 个图层 → id = layer_count - 2
  - ...
  - 最后一个图层 → id = 0

### 脚本中的引用

```
0x34 显示指令格式：
\x34 <slot(2-12字节)> \x00 <文件名>.PNA \x00 \x01 \x01 ...
```

其中 `<slot>` 的最后 2 字节是 u16 图层 id，取值范围 `[0, layer_count)`。

### 合法性判断

- ✅ **正确**：请求 id < layer_count（位置区间）
- ❌ **错误**：用 PNAP 元数据表中的 layer_id 字段集合（命中率仅 83.47%）

### 关键结论

**同名 PNA 在 Steam 版和原版中具有不同的语义**：
- 即使文件名相同（如 `COM_04L.pna`）
- Steam 版和原版的图层数量可能不同（42 层 vs 29 层）
- 图层内容和位置完全不同
- 脚本中引用的 layer_id 是基于特定版本 PNA 的位置编号

**因此**：必须使用命名空间隔离，不能让两个版本的同名 PNA 共存。

## 命名空间隔离规则

### 基本原则

1. 一旦原版和 Steam 版脚本引用了同名的 PNA，就必须为原版的 PNA 重命名为带 `ORG_` 前缀的文件
2. 原版 PNA 文件一旦改名，就必须在相应的原版脚本中修改原来的引用名为新的名称

### 事件 CG vs 人物立绘的命名要求

Steam 引擎对不同槽位的 PNA 命名容忍度不同：

| 槽位 | PNA 命名要求 | 原版资源可否用 ORG_ 前缀 | 案例 |
|---|---|---|---|
| `ev01`/`ev02`（事件 CG） | **必须是普通新名，无 ORG_ 前缀** | **否**（ORG_ 前缀必然注册失败） | `HIK_17L`/`COM_90L` ✅；`ORG_COM_04L` ❌ |
| `st01`-`st30`（人物立绘） | 接受 `ORG_` 前缀，也接受带日文名 | **是**（可正常隔离） | `ORG_B沙夜_01L`、`ORG_Aひかり_01M` 通过 |

### 实际应用

**事件 CG**（进 ev01/ev02）：
- 不能用 `ORG_` 前缀
- 若属原版新增，用 **9X 段位**标识，如 `COM_90L`

**人物立绘**（进 st* 槽）：
- 可以、且应继续用 `ORG_` 前缀做命名空间隔离
- 示例：`ORG_B沙夜_01L`、`ORG_Aひかり_01M`、`ORG_Dころな_01L`

### 命名空间隔离实例

**事件 CG（9X 段位，无 ORG_ 前缀）**：
- Steam 资源：`COM_04L.pna`（29 层）
- 原版资源：`COM_90L.pna`（Miazora COM_04L，29 层，部署时改名避免同名冲突）

两套资源共存，各自配对对应版本的脚本：
- `*_E.ws2` 脚本 → 引用 `COM_04L.pna`（Steam 版）
- `*_H.ws2` 脚本 → 引用 `COM_90L.pna`（原版，9X 段位）

**人物立绘（ORG_ 前缀）**：
- Steam 资源：`Aひかり_01M.pna`
- 原版资源：`ORG_Aひかり_01M.pna`（st 槽接受 ORG_ 前缀，可正常隔离）

## PNA 内部结构

### 图层分组机制

PNA 的图层按**动画相位分组**，通过 `u0`（unknown_0）字段标记：

- `u0 = 0`：基础帧
- `u0 = 1/2`：子图层组边界哨兵

示例（`SAY_17L`，15 层）：
```
[组A 帧 lid 13-8] → 哨兵(2) → 哨兵(1) → [组B 帧 lid 5-4] → 哨兵(2) → 哨兵(1) → [组C lid 1] → 哨兵(2)
```

### 与 LAYER_ORDER 的关系

- LAYER_ORDER 中的 blink/talk 子图层对应 PNA 为口型/眨眼动画提供的帧组数量
- 引擎在 `0x34 ev01 <PNA>` 时，会根据 PNA 内部的图层结构自动生成 `ev01/ev01blink/ev01talk` 三个子图层

**注意**：虽然 PNA 结构影响动画效果，但不是 ev01 注册成败的决定因素——问题在资源**名**而非结构。

### 二进制布局（逆向确认，见 `tool/pna.py`）

```
header: magic(4B "PNAP") unknown(i32) canvas_w(i32) canvas_h(i32) layer_count(i32)
layer_count 个 entry，每个 10 x i32（40 字节）：
  [0] u0        -- 0=真实图层；1/2=分组哨兵（无图像数据）
  [1] layer_id  -- 0x34 显示指令引用的位置量，layer_id = layer_count-1-index；哨兵为 -1
  [2..5] box_x, box_y, box_w, box_h -- 该图层在画布上的贴图位置
  [6] reserved  -- 观测样本中恒为 0
  [7..8] IEEE754 double 1.0 的低/高 32 位（图层不透明度等固定标记）；哨兵为全 0
  [9] size      -- 该图层内嵌 PNG 的字节数；哨兵为 0
图层 PNG 数据按 entry 顺序紧跟在图层表之后，size>0 的才有数据。
```

**关键结论（实测校验，见 `doc/technical-solutions.md` 4.6）**：
- `box_w`/`box_h` 恒等于内嵌 PNG 自身的像素宽高（Chip3.arc 全部 COM_04/05 系列 84 个
  非空图层验证 0 处不匹配），与 `canvas_w`/`canvas_h` 无关，是"该图层的贴图位置"不是
  "画布大小"
- `unknown` 字段 = `44 × layer_count + 12`（元数据大小，非语义字段，见 `doc/engine-mechanics.md`）
- 同一 PNA 内，`u0` 哨兵把图层分成若干组：一组通常是"1~2 个全画布主图" + "若干组共享
  同一裁切框的局部动画帧（每组对应一位角色）"
- **`u0`/哨兵不记录"哪组局部帧对应哪个全画布状态"**——这个配对关系格式里没有字段可查，
  只能靠实机测试确认（教训详见 `doc/lessons-learned.md` 第 9 节）
