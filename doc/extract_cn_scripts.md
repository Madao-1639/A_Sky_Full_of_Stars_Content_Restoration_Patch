# 从「替换启动项 exe」型汉化补丁中提取汉化文本

> 对象：民间汉化补丁（ＡＵＧＵＳＴ中文化委員會）发布的繁中单文件 exe（`miagete_cht_170416.exe`）。
> 本文 = 机制结论（正反两面）+ 关键数值速查 + 全量对账，仅凭本文即可重新执行提取。
> 持久产物：`resource/cht_text/pool.tsv`、`resource/cht_text/_cht_key_text.tsv`、`resource/cht_text/original/`（按原版行号归组的最终交付）、`tool/cht_cipher.py`。提取过程脚本已随交付定稿删除（见 §5.3）。

---

## 1. 正面：这种「只替换启动项 exe」的汉化是怎么实现的

单文件内核汉化把「翻译数据 + 改造后的引擎」全部封装进一个 exe，归档（.arc）保持原版不动。实现要点：

### 1.1 文件布局：幌子 PE + 加密 overlay

- 磁盘上的 PE 头/节区是**幌子**：`.text` 仅 60KB（混淆解包壳），`.data` 仅 16KB（加密字符串常量），`.rsrc` 保留原引擎资源（版本信息仍是 `AdvHD.exe 1.4.1.3 WillPlus`——借此可确认其引擎血统与版本）。
- 真实内容在**最后一个节区之后的 overlay**：解包壳运行时按「最后一节的 raw 偏移 + raw 大小」定位 overlay 起点（本例 0x48000）。
- overlay = **改造版引擎**（基于原版 1.4.1.2 的 AdvHD，版本资源被继承）+ **翻译数据库** + 容器元数据，全部加密/压缩。

### 1.2 混淆手段（本例实际观察到的）

| 手段 | 本例形态 |
|---|---|
| API 调用重定向 | 每个 API 调用经 `push offset <IAT>; call 解析器` 小跳板，解析器用 `_setjmp3` + 常数运算返回真地址，IDA 看不到直接 xref |
| 不透明谓词 | 大量 `imul/and 常数` 判断，恒真/恒假分支塞满垃圾调用 |
| 调用混淆 | 间接调用目标 = 常数 ÷ `adler32(日期串)`（分子分母同源，**不是日期锁**，纯混淆） |
| 字符串加密 | API 名/格式串以「8 字节密文块 + 4 字节 0」记录存于 .data，运行时逐块解密 |
| 自研分组密码 | 见 §3.2，S 盒由数据表异或常数派生，密钥由 15 字节 blob 置换出 60 字节 |
| 手工构造代码 | 最终转移前在堆上逐字节写跳转桩（`push/mov eax/call eax/mov esp`）再 `jmp eax` |

### 1.3 运行时流程

1. 幌子壳执行：解密自身字符串 → `GetProcAddress` 解析 API → `CreateFileW` 打开**自身文件** → seek 到 overlay → 校验魔数 → 解密 496 字节容器头；
2. 按头内偏移提取模块 blob（CBC 解密 + LZSS 解压）得到 **STEELBOX 模块**（带自定义重定位表的可执行映像）；
3. 从 overlay 后段按节表重建**改造版 AdvHD 引擎**（.text 1.3MB，与 Steam 版 1.96MB 不同），逐节解密/解压、重定位，手工跳转桩进入引擎入口；
4. 引擎运行时**挂钩文件读取**（CreateFileW/ReadFile/SetFilePointer 一族，另解析 NtProtectVirtualMemory 等做自保护），把原版日文脚本的文本读取重定向到 overlay 内的繁中数据；
5. 游戏启动时即把**全量繁中译文**（UTF-16LE、NUL 分隔）加载进堆内存。

**重要前提**：壳会读同目录的**原版 AdvHD.exe**——目录里只有汉化 exe 时在最终跳转处崩溃（§3.8 坑 7）。

## 2. 反面：提取这类补丁的通用流程

通用于「单文件内核汉化 / 加密 overlay / 运行时解包」类目标，分四个阶段。

### Phase 1 侦查（判断形态）

1. **PE 节区 vs 文件大小**：`sum(节 raw 偏移+大小) << 文件大小` → 有 overlay。本例：节区共 ~230KB，文件 11.6MB → 10.8MB overlay。
2. **熵分析**：overlay 熵 ≈ 8.00 → 加密或强压缩；逐块熵均匀 → 整体一层加密。
3. **明文扫描**：对 overlay 扫 UTF-16LE / Shift-JIS / Big5 / GBK 的 CJK 串。命中 → 数据明文存储，直接提取（最幸运路径）；零命中（本例）→ 必须破密码层。
4. **版本资源 / 导入表特征**：判断引擎身份（WillPlus AdvHD 的窗口函数集 + 动态 LoadLibrary DirectX 是典型指纹）；导入表齐全但 .text 极小 → 壳 + 运行时展开，而非独立程序。
5. **找原版引擎对照**：同引擎原版 exe（本例为 Steam 版资源）可对照版本、节布局、引擎字符串，快速识别「改造了什么」。

### Phase 2 定位数据与容器

1. **overlay 读取点**：在壳代码里找 `CreateFileW/CreateFileA/CreateFileMappingW/MapViewOfFile/ReadFile/SetFilePointer` 的引用（注意 API 重定向会让 xref 断链——找 `push offset <IAT 项>` 的字节模式）。
2. **容器头/魔数**：overlay 起点常见校验：dword 异或签名、CRC、版本字段。本例：`u32[0] ^ u32[4] == 0x1F040E15`（8 字节魔数）。
3. **头内自洽性校验**：偏移+大小字段应互相咬合（本例 `+32+36 == +44`、`+8 == 头结束偏移`）——咬合即解密正确的铁证。

### Phase 3 破解密码层

1. **找解密例程**：从容器头字段的使用处顺藤摸瓜（seek→read→解密→解压），解密函数通常在壳 .text 中；S 盒构建（查表异或常数）是明显指纹。
2. **警惕反编译器假象**：Hex-Rays 会内联 memcpy 习语、丢弃死存储、猜错参数类型——**关键算法必须字节级核对汇编**（本例：解密器里一个从未出现在反编译输出中的魔数常量、以及被内联的块拷贝助手）。
3. **拿 ground truth 验证**，三选一或组合：**已知明文**（格式串 `%lf`/`%d%m%Y`、API 名、魔数校验值）；**自写微型解释器**（对解密函数直接仿真执行真字节，解密例程是纯计算、无 API 依赖时最容易，单步对比自己的 Python 实现）；**动态调试**（x32dbg/x64dbg 在解密后断点读内存）。
4. **常见实现坑**（自己写解密时）：轮密钥推进（每轮换 key 字节）、字节写回只改低 8 位、CMP/TEST 不写回、SIB+disp32 寻址、CBC 链起点（每 blob 独立还是连续）、非 8 对齐的头与数据块的衔接。

### Phase 4 提取

1. **静态路径**：实现算法离线解密（干净、可复现、可写进文档）。
2. **动态路径**（更快拿到最终文本）：让目标**真实跑起来**，运行时一切解密已完成，直接读进程内存提取。minidump（`rundll32 comsvcs.dll,MiniDump`）对**被调试器附加的进程**常失败 → 用 ctypes 直读更稳；进程必须**活着**且已加载目标数据（游戏启动即全量加载文本池时最佳）。
3. **文本池结构识别**：引擎译文通常是 UTF-16LE + NUL 分隔 + 引擎控制码（本引擎为 `%K%P` 点击等待、`\n` 强制换行、`「」` 对话引号）；控制码是区分「真文本」与「解码噪声」的最好指纹。
4. **条目→剧本映射**：文本池本身只有译文；真正的对应关系要找**补丁自己的「句子 → 译文」查找机制**（本例见 §4，是索引表 + key 算式）。

## 3. 提取速查（runbook + 关键数值）

所有偏移以十六进制记；文件 = 繁中版 exe。

### 3.1 文件与壳

- 大小 11,600,814 字节；md5 `0dc958fb59e1c6b776a6ac648aa2174d`
- PE 节区：`.text` raw 0x1000+0xF000、`.rdata` 0x10000+0x2000、`.data` 0x12000+0x4000、`.rsrc` 0x16000+0x32000 → **节区结尾 = 0x48000**
- overlay：0x48000..0xB1016E，共 0xAC83AE 字节，熵 8.00，无任何明文
- 入口 0x407B84（CRT）→ `main` 0x405AD4（混淆）；解包壳关键函数：`sub_401CBE` overlay 装载器（读魔数/头/分发 blob）、`sub_40476C` 文件打开器（解密 API 名 + CreateFileA）、`sub_40289B` blob 提取器（seek→read→CBC→LZSS）、`sub_40540E` 批量 CBC 解密、`sub_4060CC` LZSS 解压、`sub_404371` 密钥置换、`sub_402425` 分组解密、`sub_40163F` 字符串解密、`sub_403FCF` 末尾手工写跳转桩 + `jmp eax`（0x4042F7）。

### 3.2 密码算法（完整规格）

```python
CONST = 0x22043E6F

def load_sbox(data):                     # 表在 .data 文件偏移 0x120D0（VA 0x4120D0）
    dw = struct.unpack_from('<256I', data, 0x120D0)
    return bytearray((dw[i] & 0xFF) ^ ((CONST >> ((i+1) % 31)) & 0xFF)
                     for i in range(256))

def perm15(blob):                        # 15 字节 blob → 60 字节轮密钥 (sub_404371)
    key = bytearray(64); p = 0; i = 11
    while True:
        key[p+0]=blob[i%15];  key[p+1]=blob[(i+1)%15]
        key[p+2]=blob[(i+2)%15]; key[p+3]=blob[(i+3)%15]
        v7 = ((i+3) % 15 + 9) % 15
        if v7 == 12: break
        key[p+4]=blob[v7]; key[p+5]=blob[(v7+1)%15]; key[p+6]=blob[(v7+2)%15]
        p += 7; i = (v7+2+9) % 15
    return bytes(key[:p+4])              # 60 字节 = 8 轮 × 7 + 尾 4

def block_dec(sbox, km, b):              # sub_402425：8 轮 + 尾循环，全部 XOR
    for r in range(8):
        k = km[7*r:7*r+7]                # 每轮推进 7 字节 ← 关键！
        v=b[3]^k[3]; b[7]^=sbox[v]
        v=b[0]^k[0]; b[4]^=sbox[v]
        v=b[2]^k[2]; b[6]^=sbox[v]
        v=b[1]^k[1]; b[5]^=sbox[v]
        v=b[4]^k[4]; b[1]^=sbox[v]
        v=b[4]^b[5]; b[2]^=sbox[v]
        v=b[6]^k[5]; b[3]^=sbox[v]
        v=b[7]^k[6]; b[0]^=sbox[v]
    for j in range(4):                   # 尾循环用 key[56..59]
        v = b[j] ^ km[56+j]
        b[j+4] ^= sbox[v]

def cbc(sbox, km, buf):                  # sub_40540E：P_i = D(C_i) ⊕ C_{i-1}，IV=0
    out = bytearray(); prev = bytearray(8)
    for i in range(0, len(buf)-len(buf) % 8, 8):
        c = bytearray(buf[i:i+8]); b = bytearray(c); block_dec(sbox, km, b)
        out += bytes(x^y for x,y in zip(b, prev)); prev = c
    return bytes(out)

def lzss(src, dstlen):                   # sub_4060CC
    out = bytearray(); i = 0
    while i < len(src) and len(out) < dstlen:
        b = src[i]
        if b == 0x80: out.append(src[i+1]); i += 2                # 转义字面量
        elif b != 0:                                             # 回溯引用
            w = struct.unpack_from('<H', src, i)[0]
            dist = (w >> 4) + 15; ln = w & 0xF
            for k in range(ln): out.append(out[len(out)-dist+k])
            i += 2
        else:                                                    # 字面量串
            cnt = src[i+1] + 1; out += src[i+2:i+2+cnt]; i += 2+cnt
    return bytes(out)
```

两把密钥（同一算法、不同 blob）：**overlay 密钥** = `perm15(文件 0x48376..0x48385)`（= overlay 头明文坐标 +368 的 15 字节 blob，**保持加密态**直接置换）；**字符串密钥** = `perm15(.data 0x12030..0x1203F)`（解密 .data 内 API 名/格式串用）。

### 3.3 overlay 容器头（0x48008..0x481F8，CBC 解密 46+14 块）

- 0x48000..0x48008 魔数：`u32[0] ^ u32[4] == 0x1F040E15`（明文不加密）
- 头明文（相对 0x48008）：`+0 = 0x0011DBFD`；`+8 = 0x481F8`（头结束文件偏移）；`+32 = 0x48338`（blob 偏移）；`+36 = 0x3F778`（blob 大小）；`+44 = 0x87AB0`（结束偏移，自洽 ✓）；`+40/+52/+108` CRC 类；`+368..383` 密钥 blob（不解密）；`+452 = 0xB103A6 ≈ 文件大小-8`
- 解密范围：`+0..367`（46 块）与 `+384..495`（14 块）——中间 16 字节是密钥区

### 3.4 STEELBOX 模块 blob（0x48338..0x87AB0）

CBC 解密（overlay 密钥）→ 首 dword = 0x59600（解压后大小）→ LZSS 解压 = **366,080 字节 STEELBOX 模块**（魔数 `"STEELBOX"`，含自定义重定位表：`[u32 目标偏移][u32 计数]` + 计数个 u16 项，`type = 项>>12` 须为 3，修正 `*(base+目标+（项&0xFFF)) += base差值`，见 `sub_4038A8`）。

### 3.5 引擎容器（0x87AB0..EOF，region2，11,045,112 字节）

0x87AB0 起独立 CBC（overlay 密钥）解出**明文描述符**：

- `+0x00 = 0x400`；`+0x04 = 0x200`（FileAlignment）；`+0x08 = 0x1000`（SectionAlignment）
- `+0x14 = 0x16A8C0 / +0x18 = 0x190`（导入表 RVA/大小）
- `+0x1C = 0x1C6000 / +0x20 = 0x31095`（.rsrc VA/大小 → **复用外壳文件资源**）
- `+0x58 = 0x140860`、`+0x5C = 0x1C`、`+0x64 = 0x159130`（用途未完全确认）
- **节表 @0x8C，步长 40 字节**：`[name8][chars4][va4][vsz4][rawsize4][off4][size4][crc4][flags4]`

| 节 | va | vsz | 数据偏移 | 数据大小 |
|---|---|---|---|---|
| .text | 0x1000 | 0x13E1FA | 0x12C | 0x93DA4 |
| .rdata | 0x140000 | 0x2D0A4 | 0x93ED0 | 0x1227F |
| .data | 0x16E000 | 0x7068 | 0xA614F | 0xF87 |
| .rsrc | 0x176000 | 0x31095 | 0（复用） | — |

（偏移连续自洽：0x12C+0x93DA4=0x93ED0 ✓）
节数据的压缩层**尚未完全确认**（直接 LZSS 的 CRC 不匹配）——不影响文本提取。
引擎重建后与内存镜像一致：`.text` 0x401000-0x53F200、镜像大小 0x1F8000。

### 3.6 动态运行与内存提取（拿到文本的最短路径）

1. **目录要求**：汉化 exe 与**原版 AdvHD.exe 同目录**（缺原版 → 崩溃，异常地址无模块归属；断点 `0x4042F7` 处 `jmp eax` 可观察转移）。
2. 运行游戏。启动即加载全量译文。
3. **对活动进程全量转储**（不杀进程）：ctypes `VirtualQueryEx` 枚举 + `ReadProcessMemory`。`rundll32 comsvcs.dll,MiniDump` 对被调试器附加的进程会失败，用 ctypes 直读。
4. **定位文本区**：转储中搜 UTF-16LE 的 `%K%P`（引擎控制码，噪声免疫）。主文本区是一块 2.6MB 连续内存——它就是补丁模块的 `.rdata`（模块运行时基址 0x02DD0000，`.rdata` RVA 0x4C000 ⇒ VA 0x02E1C000），布局与用法见 §4。
5. **解析**：串区 = UTF-16LE、NUL（0x0000）分隔的字符串序列，逐条 `read u16 until 0x0000` 走到区尾，过滤含代理对的乱码条目。**串序不是剧本序**，条目→剧本的对应必须走补丁自己的索引表（§4），不能按位置推算。
6. 产物口径：串区共 **42,748 条**；落盘 `pool.tsv` 为 **42,511 条**（**42,371 条以 `%K%P` 结尾**的剧本行 + **140 条 `%LF` 说话人名**；串区与 pool.tsv 的差集 = 59 种省略号短句与个别 %LF 名，见 §5.4）。

### 3.8 坑清单（都真实踩过）

1. **x96dbg 系 MCP 插件打印的地址是十进制却带 `0x` 前缀**；参数名也与常规不同（`SetBreakpoint` 用 `target` 不是 `address`；`SearchForStrings` 用 `searchText/encodingType/startAddress`，encodingType 只认 `ascii|utf16`）。走 streamable-http 直接 POST JSON-RPC 到 `/mcp`，无需 SSE。
2. **rundll32 comsvcs MiniDump 对被调试进程失败** → ctypes `ReadProcessMemory` 直读（不杀进程、不依赖调试器）。
3. **Hex-Rays 反编译假象**：memcpy 习语被内联、死存储被丢弃（本例解密器中的 `0x4621D90C`）、小函数参数猜错——关键逻辑必须核对原始字节。
4. **字节级正则误用**：`re.compile('pattern'.encode('utf-16le'))` 里 `\uXXXX` 会被当字面文本——要么用真实字符构造 pattern 再 encode，要么先整体 `decode('utf-16le')` 再用 str 正则。
5. **自写 x86 解释器踩过的四个真 bug**：`cmp` 写回了结果（cmp/TEST 不写）、`mov r8,[mem]` 清零了寄存器高 24 位、group1(0x80-0x83) 把 reg 字段（操作码扩展）当寄存器操作数、F7 分支尾部 `eip = size` 覆盖了 TEST 的 `eip = size+4`。
6. **密码实现最大坑**：8 轮的**轮密钥推进**（每轮 `key[7r..7r+6]`）——静态读汇编时极易把 8 轮看成同一组 key。
7. **崩溃排查不要先入为主**：曾误判为「日期锁」（main 里确有日期参与除法混淆，但分子分母同源、与日期无关）；真因是**目录缺原版 AdvHD.exe**，放回原版即可正常运行。

## 4. 民汉繁中的「句子 → 译文」查找机制

繁中池本身**不带剧本名、串序也不是剧本序**，按位置推算对应关系已被证伪（同一场景相邻两行的串 id 升降各半；按剧情顺序的相邻场景串区间全部重叠）。真正可靠的对应关系是**补丁自己内置的查找机制**，机制如下。

### 4.1 补丁模块与运行时索引表

补丁本体是从内存分页重建的独立 PE 模块（7 段齐全；原始 ImageBase 0x10000000，运行时重定位到 **0x02DD0000**，SizeOfImage 0x2EB000，入口 RVA 0x2240）。其 `.rdata`（RVA 0x4C000，运行时 VA **0x02E1C000**）就是启动后看到的那块 2.6MB 文本区：

| 区间（块内偏移） | 内容 |
|---|---|
| `0x0 .. 0x160` | 配置/字幕模块的字符串（`.\\Patch.ini`、`invalid subtitle format`、`vsfilter.dll` 等）|
| `0x160 .. 0x59EA0` | **45,992 条 8 字节记录**：`<u32 key><u32 off>`，按 key 升序 |
| `0x59EA0 .. 0x59EA4` | 结束标记 `0xFFFFFFFF` |
| `0x59EA4 .. 0x27A5E6` | 繁中译文串区，UTF-16LE + 空结尾，紧密排布，共 **42,748 条** |

查表方式：显示句子时算出 key，从第 0 行起**线性前扫**升序表，`目标 < 当前 key` 即退出（不是二分）；命中则译文地址 = 串基址指针 + off。数量口径：表 45,992 条记录 / **45,981 个不同 key** / 指向 **42,570 条不同译文**（178 条串未被引用）。

### 4.2 key 算式（已破解，双正对照验证）

哈希函数（补丁模块 0x02DD1070 起；`T` = 256 项 u32 表，RVA 0x4B1E0）：

```
v6 = 0xEEEEEEEE;  i = 0x7FED7FED;  hasHigh = 0
for (每个字节 c) {                      // 0x02DD1070..0x02DD1155
    v9 = v6 + i;
    if (c >= 0x81) hasHigh = 1;         // SJIS 双字节判定
    i = T[c] ^ v9;
    c = *++p;  if (!c) break;           // 最后一个字符不执行下面的增量
    v6 = i + c + 33*v6 + 3;
}
if (hasHigh && i) {
    key = strncmp(s, "%LF", 3) ? (i ^ a1) : i;    // %LF 人名不 XOR
    查表;                                // 未命中 → 显示日文原文
}

key = key_hash(char 文本字段整串, T) ^ (字段在解码后 .ws2 流里的字节偏移)
```

两个硬性细节：

1. **哈希输入是 NUL 定界的整个字段，包含结尾的 `%K%P`**。按 `%K%P` 截断会算出完全不同的 key（早期所有负结果的根因）。
2. **`hasHigh` 是硬门槛**：串里没有一个 `>= 0x81` 的字节就根本不查表（原版 8 条纯 ASCII 的 `%P` 行因此无对应，见 §5.2）。

`a1` 的定性（被否假设：全局常量 / 脚本名哈希 / 成员序号 / 行号 / 记录头两字节）：对每个成员放开基址联立求解，只有 **`a1` = 字段在解码后 .ws2 流里的字节偏移（B = 0）** 能做到抽样 200/200 一致且大成员全部可查表行 100% 命中（如 `yozora_ori_118_H` 816/816）。两条独立正对照：**UI 小表 10/10**——.data RVA 0x4B000..0x4B1E0 另有 60 槽 UI 小表（10 项指针落繁中串区），key 为**纯哈希不 XOR**，用原版全部文本片段（80,121 条）撞其 10 个 key，10 条全中（假阳性期望 0.0002）；**%LF 人名分支**——同一语料按 `a1=0` 撞主表 45,981 个 key，命中 143 条且全部是 `%LF` 说话人名、台词 0 条，与「人名不混偏移」分支的预测一致。

### 4.3 引擎侧挂钩位置

引擎镜像（基址 0x00400000）中 `0x004D19C5` 原为 `call 0x004B9070`，被改写为 `call 0x0051E464`。shim 逻辑：`mov eax,[esp+10]` → `push [esp+4]` → `push [eax]` → `call [0x0056E280]`（导入表，进补丁模块查表）→ `test eax,eax; je 0x004B9070`——**查不到就跳回原函数，显示日文原文**；非空时量出 UTF-16LE 串长（`cmp word[edx],0 / lea edx,[edx+2] / sub / shr 1`）连同串地址交给 `0x004077E0`。`push [eax]` 传入的 dword 就是上式的 `a1`（字段字节偏移）。

### 4.4 已排除的路线（结论，脚本可复现）

| 猜测 | 结果 |
|---|---|
| 常见哈希直接算 key | 13 函数 × 6 编码作用于全部唯一日文句，最高命中 2 条（随机水平） |
| key = 常见哈希(文本+位置字段) | 962 种构造组合，最高命中 1 条（随机水平） |
| 补丁文件里带日文原文可直接配对 | 按 SJIS/UTF-16LE 搜全部解密产物，0 命中——补丁只带译文 |
| 内存里有「行号→条目号」位置数组 | 全转储扫描，最长连续段远小于 4 万 |
| 内存里存有日文原文可配对 | 500 次探针扫全部转储区域，仅引擎自身文本块偶然命中 |

结论：补丁不带原文、key 混有位置信息，是在显示时**现场算 key**——算式只能从模块代码读出（即 §4.2），凑不出来。

## 5. 全量对账（最终口径，全部由脚本重算）

### 5.1 原版口径统一

- `Rio.arc` 里 0x14 `char` 台词共 **45,856 条**（常被引用的 45,844 是「串内含 `%K%P`」的正则口径：漏 8 条纯 `%P` 行、4 条以 `%K` 收尾的行，45,844+8+4=45,856）。
- 说话人名是独立的 `\x15 %LF<名>\x00` 记录：**25,841 次出现、144 种**。
- 语音记录为 `\x28 "char" <ID>\x00<OGG>`，台词匹配正则须写成 `\x14....char\x00` 才能排除。

### 5.2 对账闭合

| 项 | 数值 |
|---|---|
| 台词 45,856 → 命中 | **45,848** |
| 未覆盖 | **8**（纯 ASCII `%P` 行，补丁按 `hasHigh` 设计跳过）|
| 表 45,981 key 的消费 | 台词 45,837 + 人名 144 = **45,981，剩余 0** |
| 回读校验 | key/pos 重算不符 0；`jp` 无法严格还原 0；`cht` 与串区原文不符 0；行号不连续 0；人名校验失败 0 |
| 人名 | 25,841 次出现全部命中 |

同形性佐证（原版日文句重复次数 vs 表内每译文的 key 数）：`[577,125,112,52,51,48,44,43,41,35,30,24]` vs `[581,124,112,60,54,50,49,43,39,34,31,24]`——两条分布基本重合，支持「表是每个出现位置一行」。±4 的偏差来自我方提取漏掉的极短记录，以及不同日文句被译成同一句中文时的次数叠加。

**「同一句日文必然落到同一条译文」不成立**（错在民汉一侧）：命中行里 42,562 个不同日文串中有 **364 个**被译成 2 种以上中文（合计 819 种译法），基本是译风差异（拟声词写法、称谓语气取舍），按本项目口径不算缺陷。映射的唯一性只按**出现次**保证（交付正是如此）。

### 5.3 交付：`resource/cht_text/original/`

生成后经回读校验（key 可按公式重算、jp 逐字节无损回编码、cht 与池内原文逐字一致、行号连续 0..N-1）：

| 文件 | 内容 |
|---|---|
| `{脚本名}.json` × 294 | 原版行号 → `{jp, cht, key, pos}`；补丁不查表的行给 `cht/key = null` 占位，保证行号连续 |
| `mapping.tsv` | 摊平 45,856 行 `stem line pos key jp cht` |
| `names.tsv` | 144 个人名 key → 民繁名 |
| `unmapped.tsv` | 8 条纯 `%P` 行 |

本套交付**只留数据、不留脚本**：生成 `original/` 的映射脚本、各校验/对账脚本与探针在交付定稿后已全部删除。提取过程不需要脚本存档——本文 §1–§5 记录了完整算法与验证锚点，配合原版游戏文件与 `tool/cht_cipher.py` 即可重新执行全程；`_cht_hash_table.json` 与 `_cht_key_text.tsv` 是查表机制的固化锚点（见 `resource/cht_text/README.md`）。

### 5.4 已定性的分歧

1. **4 行演出控制符**：全归档只有 4 行以 `%K`（无 `%P`）收尾，民繁侧 4/4 在末尾补了 `%P`（`yozora_com_402` 206、`yozora_com_A_101` 189、`yozora_com_A_103a` 102、`yozora_com_B_103a` 130）。采纳时要决定是否保留原版收尾。
2. **`pool.tsv` 少 59 条**：串区被引用 42,570 条，`pool.tsv` 只有 42,511 条，差的是「……」类省略号短句与个别 `%LF` 名（被引用 788 次）；`original/` 直接引串区不受影响，沿用 `pool.tsv` 的旧脚本要注意。
3. **覆盖率 ≠ 可直接部署**：本机制只回答「民汉这里显示哪句中文」，没有回答译得对不对、繁简与引号是否合本项目约定，也没有处理 `*_E` 场景与 Steam 版的行号漂移（§6.3）。

## 6. 与简中补丁的关系、遗留与未决

### 6.1 繁中池是独立民译（基线对照）

折叠简繁 + 引号归一后**逐字全等**的对照（只统计池内唯一形）：

| 中文来源 | 行数 | 折叠后与池全等 | 比率 |
|---|---|---|---|
| Steam 官方简中（未改动）| 34,693 | 1,163 | **3.4%** |
| 简中补丁新增部署的还原场景（52 个成员）| 11,267 | 3,751 | **33.3%** |
| 官方有、简中补丁未部署的脚本（35 个）| 4,137 | 157 | 3.8% |

结论：繁中池**不是**官方简中的繁体化（3.4% 只够覆盖短句），是**独立民译**；还原场景与池的相同率是官方基线的约 10 倍 → 简中补丁的还原译文与繁中池真实同源。那 52 个成员在官方中文里不存在（Steam 把对应脚本砍剩残本，如 `yozora_hika_103d_H_E` 只剩 120 条文本记录，民繁该场景 393 行），不存在「两边都抄同一份官方中文」的假象。
试点抽读中，简中补丁对民繁文本的改写整体不劣于民繁（「温度→溫柔」类误译、主语颠倒、破碎句均已修正）；逐场景的实质分歧行仍需以日文原文为仲裁逐行核对。

### 6.2 行号坐标：`*_E` 场景与原版不是同一套

`.ws2` 里 0x14 记录的 `idx` 是该脚本自己的 `.lng` 索引；简中补丁的 `.lng` 行序跟着部署在 asset 里的脚本，而 Steam 版在多处增删了文本记录：三方计数（原版 / 部署 / `.lng`）**224 个场景一致、70 个场景不一致**（70 个全部是 `*_E`）：59 个记录数本身就不同（如 `yozora_com_201a` 原版 118 条、部署与官中 122 条），11 个记录数相同但 `.lng` 更长（如 `yozora_com_A_101` 189/189/192）。计数一致只是**必要条件**（删几条又插同样多条看不出来），224 个「一致」场景的行号**可用但未经逐行验证**。归一要靠 `resource/seam-diffs.json` 已有的 `orig_idx`/`steam_idx` 对照，或语音/演出锚点对齐。

### 6.3 采纳繁中行的前置工序（尚一行未采纳）

1. 译名映射以民汉 `NameTable.txt` 为准（繁中 可樂娜/曉哥 ↔ 简中 来露娜/晓斗）；
2. `「」` → `“”` 引号转换（民汉简中约定）；
3. 繁→简用 `resource/cht_text/_t2s_seed.json`（300 对人工校验种子）复核；
4. **Steam 官中文本禁止改动**——繁中池只对简中补丁自己新译/还原的行有意义；
5. 处理 §6.2 的行号漂移后再谈部署；`script/final_verification.py` 尚未在新口径下重跑。

### 6.4 未决事项

1. **来源矛盾（未决）**：项目文档对还原文本来源的记载相互矛盾（一作「译自英文、未经人工校对」，一作「校对时参照了繁中用语」）；实测同源信号（§6.1 的 33.3%）与后者相符但不能定论，需以原始参考文本、民汉池、简中文本三方对照逐场景溯源。
2. **region2 节数据的压缩层**未确认（不影响文本提取）；STEELBOX 模块的完整用途、引擎容器描述符的 `0x140860/0x1C/0x159130` 三字段语义未查。

### 6.5 不入库物

大型二进制（进程转储约 250MB、解密出的 STEELBOX 模块、重建的引擎镜像与补丁模块镜像）不入库——体积大，且补丁模块是民汉组的产物、不该由本仓库再分发；需要时可由 §3–§4 的算法复算。
